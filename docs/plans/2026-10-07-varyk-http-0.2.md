# varyk-http 0.2 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build `varyk-http` 0.2 on varyk 0.8: `Time` and `Uuid` as path and query parameters, bytes in and out (request and response bodies, multipart parts, binary WebSocket messages, the client), and the `users` demo with `created_at: Time`.

**Architecture:** No new file and no change to the root surface of `src/lib.vr`. `message.rs` gains the two `Plain` impls, the bytes calls of `Request` and `Response`, and a raw-bytes body that `read_back` keeps; `live.rs` gains `Part::bytes` and `Part::content_type`, the `Message` enum, `send_bytes`, and `recv_message`; `client.rs` gains `post_bytes` and `put_bytes`. Every bytes call is the twin of a text call and shares its private path.

**Tech Stack:** Varyk 0.8 and `varyk-std` 0.8 (unreleased: the compiler from `/Users/vlad/projects/varyk/varyk` branch `feat/milestone-5c`, numbered 0.7.0 until its release), `varyk-sql` 0.3 for the demo (unreleased: `/Users/vlad/projects/varyk/varyk-sql` branch `feat/varyk-sql-0.3`), Rust 1.85+, axum 0.8.9, multer 3, reqwest 0.12, tokio-tungstenite 0.29. No new dependency.

**Spec:** `docs/specs/2026-10-07-varyk-http-0.2-design.md` ("spec §n"), the authority; it extends `docs/specs/2026-10-06-varyk-http-design.md` ("0.1 §n"). Its compiler side is `Varyk-Lang/varyk`'s `docs/specs/2026-10-07-milestone-5c-design.md` ("M5c §n"), sections 2 (the types and where they go), 2.5 (facade forms), 5 (`varyk-std`: `FromStr`, the `bytes::Bytes` conversions), 6.1 (this package's contract), and 6.3 (release order). ## Review Focus

Inputs the spec implies but its test list does not name, most likely to bite. Each has a test in its owning task.

1. A `Time` with an offset: in a path, `/at/2026-10-07T12:00:00+02:00` reads as `2026-10-07T10:00:00Z`; in a query, `%2B02:00` reads the same, and a raw `+` is a space by form encoding, so the 400 naming the decoded text. Task 1.
2. `Response::bytes(b, "image/png\r\nx-evil: 1")` (the line break built from JSON as the multipart tests do): the fixed 500 with the reason logged, never a split header. Task 2.
3. A part whose declared `Content-Type` multer cannot parse (`not a type`): `content_type()` gives that text, not `None`, since it is the client's word and not checked; a part with no `Content-Type` gives `None`. Task 3.
4. A binary message over the body limit read by `recv_message`: closed with 1009 and `None`, as `recv` does. Task 4.
5. `client.post_bytes(url, b, "a\r\nb")`: an `Err` before anything is sent, naming no path or query, never a panic. Task 5.

## Development Approach

- TDD per task: Varyk `#[test]`s in `src/tests.vr` first, through `app.request`, or `serve` on the task's loopback port; see them fail, implement, see them pass. Rust `#[cfg(test)]` tests only for the WebSocket conversation (task 4), in `live.rs`'s existing module.
- Bytes that are not UTF-8 come into a Varyk test from `Bytes::from_base64` of a literal, through one helper in `src/tests.vr` that turns its `Result` into a `Bytes`. Varyk cannot join `Bytes` (M5c §2.6), so a multipart body holding such bytes is one base64 literal of the whole form, computed once, with its decoded form in a comment.
- Patterns: the `Plain` impls follow the integer ones; each bytes call mirrors its text twin (`body`/`set_body`, `text`, `send`, `post`/`put`) and shares one private path with it: one file read for `body` and `body_bytes`, one field read for `text` and `bytes`, one read loop for `recv` and `recv_message`, one frame send for `send` and `send_bytes`, one client `send` with an optional typed body. Error messages are the twin's.
- Not needed: anything in spec §7 (a raw-body handler parameter, streaming bytes, `patch_bytes`, binary events, checking a part's declared type); a new dependency (axum's `Bytes` is the `bytes::Bytes` `varyk-std` converts from); a change to `src/lib.vr` or `src/server.rs`; derives on `Message` beyond what Varyk's `match` needs.
