# varyk-http 0.2: time, ids, and bytes

Date: 2026-10-07.

**Status.** Implemented, not yet released. Extends
`2026-10-06-varyk-http-design.md` ("0.1 §n"), whose rules stay in force
except where this spec replaces them. Its compiler side is Varyk
milestone 5c (`Varyk-Lang/varyk`,
`docs/specs/2026-10-07-milestone-5c-design.md`, "M5c §n"), whose section
6.1 is the contract this spec implements. Varyk is experimental and
pre-1.0: anything here may change.

## 1. Summary and scope

Varyk 0.8 brings `Time`, `Uuid`, and `Bytes` (M5c §2). 0.2 takes them
where HTTP needs them:

- a `Time` or `Uuid` as a path or query parameter (section 2), which is
  the one part the compiler depends on;
- bytes in and out: request and response bodies, multipart parts,
  binary WebSocket messages, and the client (section 3), which 0.1 §9
  left for this release;
- the `users` demo with `created_at: Time` (section 4), which meets
  milestone 5's bar.

```varyk
async fn avatar(id: Uuid, state: Shared<State>) -> Result<http::Response, Error> {
    let found: Option<Bytes> = state.db.first("select avatar from users where id = $1 and avatar is not null", id).await?;
    match found {
        Some(b) => Ok(http::Response::bytes(b, "image/png")),
        None => Err(http::not_found("no avatar")),
    }
}
```

### 1.1 Decisions

- **New calls beside the text ones.** 0.1 §10 asked whether bytes take
  the existing calls or new ones. Varyk has no overloading, and the
  server's `Response` is also what the client gives back, so a
  constructor `Response::bytes` and a reader of the same name cannot both
  exist. Every text call stays as it is; each bytes call has its own
  name, ending in `bytes` (section 3).
- **`recv` stays text; `recv_message` takes both.** A text-only handler
  keeps `while let Some(text) = ws.recv().await?`, and a handler that
  takes binary messages asks for them by name.
- **A content type is always written.** `Response::bytes` and the
  client's bytes calls take one, so no binary body goes out without a
  declared type.

## 2. Path and query parameters

`Plain` (0.1 §6.2) is implemented for `varyk_std::Time` and
`varyk_std::Uuid`, through their `FromStr` (M5c §5), so `param` and
`query` give them, required or as an `Option`. A value that does not
read is the 400 of 0.1: `{"error": "the path parameter `id` cannot be
read from `abc`"}`.

## 3. Bytes

Every call takes a `Bytes` as `&varyk_std::Bytes` (M5c §2.5): the
caller's value is not moved, and the package keeps a handle to the same
buffer, with no copy.

| Call | Gives |
|---|---|
| `req.body_bytes()` | `Bytes`, the body as it came, with no copy; empty for a multipart form, as `body()` is |
| `req.set_body_bytes(b)` | sets the body, for a request made with `http::Request::new` and sent with `app.request` |
| `http::Response::bytes(b, content_type)` | a 200 with the body `b` and that `content-type`, set as `set_header` sets a header, and `x-content-type-options: nosniff`, as a file response has |
| `r.body_bytes()` | `Bytes`, the body `r.body()` reads, with no UTF-8 check: what `app.request` or the client gave back, or for a response a handler built, its bytes, a file's content read whole, and empty for an event stream |
| `part.bytes().await` | `Result<Bytes, Error>`, the part's whole content, under the body limit and read once, as `text` is |
| `part.content_type()` | `Option<string>`, the type the client declared for the part, its word and not checked |
| `ws.send_bytes(b).await` | `Result<bool, Error>`, one binary message, as `send` |
| `ws.recv_message().await` | `Result<Option<http::live::Message>, Error>`: the next message, text or binary; `None` as `recv` gives it |
| `client.post_bytes(url, b, content_type).await`, `client.put_bytes(url, b, content_type).await` | `Result<http::Response, Error>`, as `post` and `put`, with `b` as the body |

**`http::live::Message`** is a Rust enum, `Text(String)` or
`Binary(varyk_std::Bytes)`, matched in Varyk:

```varyk
while let Some(message) = ws.recv_message().await? {
    match message {
        http::live::Message::Text(text) => ws.send(text).await?,
        http::live::Message::Binary(b) => ws.send_bytes(b).await?,
    };
}
```

It is declared in `src/live.rs` and reached through `http::live`, as
`Part` is; it is not named at the package's root, which keeps the
root's binding rule (M5b4 §6.1) about structs alone. Ping, pong, close,
the limit, and malformed messages behave as 0.1 §2.5 says for `recv`.

**What stays.** `req.body()`, `r.body()`, `part.text()`, `ws.recv()`,
`ws.send(text)`, `Response::text`, `Response::json`, the client's JSON
`post`, `put`, and `patch`, and server-sent events, which are text by
their format. `ws.recv()` still closes the connection with 1003 when a
binary message comes, and its README row points to `recv_message`.
`r.body()` stays empty when the body is not UTF-8.

**What is fixed.** A response's body is now kept as bytes when it comes
back from `app.request` or the client (0.1 keeps it as text, so a binary
body was lost); `r.body()` reads it as text, as before.

A `Bytes` passed to the JSON calls, `Response::json(b)` or the client's
`post(url, b)`, or returned by a handler, is sent as a JSON string of
base64 (M5c §2.3), as any value is; the README says to use the bytes calls for a raw body.

## 4. The demo

`demo/users` gains `created_at: Time`, set by `Time::now()` when a user
is made, in a `text` column on SQLite, written by `varyk-sql` 0.3. Its
tests stop comparing the exact JSON of a user: they read the body into
`User` and check its fields, and that `created_at` lies between two
`Time::now()` calls made around the request. This meets milestone 5's
bar (M5c §9): a `created_at` that is a `Time`, read through `varyk-sql`.

## 5. Testing and definition of done

- A `Uuid` path parameter and an `Option<Time>` query parameter, each
  read and each giving the 400 for text that does not read.
- `body_bytes` and `set_body_bytes` with bytes that are not UTF-8,
  through `app.request` both ways; `Response::bytes` with its
  `content-type`; `r.body()` empty for that body.
- A multipart part with bytes that are not UTF-8 read by `part.bytes()`,
  its `content_type()`, and a part over the body limit giving the 413 as
  `text` does.
- WebSocket: `send_bytes` and `recv_message` both ways, and `recv`
  still closing on a binary message with 1003; the Rust test
  `a_binary_message_closes_with_1003` keeps its name and gains a
  `recv_message` twin.
- The client's `post_bytes` and `put_bytes` against a loopback server on
  the next free ports (from 41820), and `r.body_bytes()` of a binary
  response.
- The demo's tests as section 4 sets out.
- README: Requests and responses, WebSockets, Uploads, and the client
  tables gain the calls; the users program at the top, its migration,
  and the `curl` outputs follow the demo's `created_at`; the status
  line, Install, and the Dockerfile name varyk 0.8, and the Versions
  table gains `0.2 | 0.8`.
  AGENTS.md and CONTRIBUTING.md: varyk 0.8 in place of 0.7, and the
  contract named as section 6 of the 5b4 spec with M5c §6.1.
- The 0.1 spec's §9 bytes item and its §10 bytes question each gain a
  line pointing here.
- CI and the release workflow: `cargo install varyk --version '^0.8'`;
  `varyk-std = "0.8"`; the
  demo on `varyk-sql` 0.3; green on stable and 1.85.

Done when CI is green, 0.2.0 is on crates.io, and the `varyk-http` item of
the roadmap's 5c entry in `Varyk-Lang/varyk` is checked.

## 6. Release

`feat!:`, since the package needs `varyk-std` 0.8. Released after varyk
0.8.0 and `varyk-sql` 0.3.0 are on crates.io.

## 7. Not in this version

A handler parameter bound to the raw body (M5c §2.6); streaming a bytes
body in pieces; a `patch` with a bytes body; binary server-sent events,
which the format does not have; checking a part's declared content type
against its content.

## 8. Decisions

Taken with the user on 2026-10-07:

- Binary WebSocket messages through a new `recv_message`; `recv` stays
  text.
- The design of sections 2 to 5, and the names of section 3.
